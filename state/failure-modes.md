# 已知失败模式与对策

> 从 37 轮实践中归纳。**读这份清单比读 37 条决策更快。**
> 每种模式都至少真实发生过一次，且多数重复多次。

---

## FM-1 · 路径假设错误（出现 20+ 次，最高频）

**表现**：脚本 `cd "$(dirname "$0")"` 后又用裸相对路径 `state/xxx`，
文件找不到；而检查写成 `[ -f X ] && ...` 会**静默跳过** → 得出"没问题"。

**典型后果**：
- Round 9：无副作用自检监控空文件 → 永远报告"未改动"
- Round 6：防空转测试没准备副本 → 报"✓ 有效（0 条日志）"
- Round 8：回归测试把临时版本覆盖到真实备份

**暗号**：某个检查"永远通过"，或耗时异常短（如 19ms 跑完需 1.7s 的活）。

**对策**：
- 写检查前先问：这个脚本的 cwd 在哪？
- 状态文件用 `../state/` 或绝对路径
- 覆盖不足时**显式告警**，不静默通过
- 自动防护：`scripts/lint-paths.sh`（已纳入回归）
  - **Round 38 补强**：原实现只检查"会 cd 的脚本"，
    不 cd 却用相对路径的脚本被漏检。现两类都查，并标注 `(cd)` / `(no-cd)`。
    已用两个坏样本验证两类都能命中。
  - **Round 60 新增防护**：`scripts/test-isolation-check.sh <副本目录>`
    在跑隔离测试前自检：致命路径泄漏（/root/projects/.dsh、/sdcard）、
    PATH 覆盖、桩可执行性。分级（致命/警告），退出码 1 = 结果不可信。
    三个场景验证通过：泄漏副本报错、部分引用给警告、完全隔离通过。

## FM-2 · 测量方法与被测对象不匹配

**表现**：用错工具测对的东西，且不自知。

**实例**：
- Round 4：用 `--max-time 6` 测中位 5.16s 的端点 → 50% 假失败率
- Round 7：`--resolve` 探测失败，但写 hosts 后实际可用
- Round 36：自写计时函数报 19ms，实际 1.7s（因为未检查退出码，失败被当成功）

**暗号**：故障"随机且难复现"、数据与直觉矛盾。

**对策**：先怀疑探针，再怀疑环境；用两种方法交叉验证。

**实例（Round 77）**：`dumpsys diskstats` 的 per-app 体积不随卸载更新，
累加 22GB 而 `df` 实测 15.2GB。若相信它，会去清理并不存在的 2GB"残留"。
**凡是要据此采取行动的数值，必须有两个独立来源且相互吻合。**

### FM-2 的四个具体形态（Round 100-130 归纳）

**2a · 输出截断把结论切掉**
`sed -n '/标题/,+4p'` 只取 4 行，而目标条目排在第 5 位 ⇒ 误判"功能没生效"。
→ **对策**：查"某个条目在不在"时用 `grep -c`，别用区间截断。

**2b · 子串包含导致条件恒真/恒假**
`if 'running' not in stdout` —— `not running` 里也含 "running"。
→ **对策**：用 `startswith` / 全词匹配，别用裸子串。

**2c · grep 自匹配（探针污染）**
`ps | grep vivo.browser` 把自己的查询命令也匹配进去。
→ **对策**：用 `scripts/proc-find.sh`（读 /proc 并排除自身 PID）。

**2d · 统计窗口选错，把历史当现状**
7 天窗口含已移除账户的错误 ⇒ 主模型"5%"（实际近 2 天 1%）。
反向：`qodercn` 曾 879 次请求、突然归零，用"近 2 天零流量"判断会漏掉"曾活跃"这一关键。
→ **对策**：短期判现状、长期判趋势，**两个窗口并列显示**，不下单一结论。

### FM-2 的使用方法（自查三问）
1. 这个数字/状态是**直接读到**的，还是**我加工出来的**？
2. 若我加工过，**加工逻辑**（截断/子串/窗口/自匹配）会不会扭曲它？
3. 有没有**第二个独立来源**能佐证？

## FM-3 · 验证手段改变被验证的世界

**表现**：跑"检查"时产生了副作用。

**实例**：
- Round 2：探测失败 → 删除可用映射（用测量驱动破坏）
- Round 8：导出测试推送临时版本 → 覆盖真实备份
- Round 9：回归里调用的脚本本身会写状态

**对策**：
- 检查工具默认只读
- 会写状态的动作要显式开关（如 `ALYX_NO_REDUNDANT=1`）
- 被检查者自查：`verify.sh` 记录前后 md5 指纹做比对

## FM-4 · 基于不可靠判断执行破坏性操作

**表现**：把"探测失败"直接当成"该删掉"。

**实例**：Round 2 host 工具删映射；Round 3 `kill $(cat pidfile)` 可能误杀
PID 复用的无关进程。

**对策**：
- 破坏前验证目标真实性（读 `/proc/<pid>/cmdline`）
- 失败安全：不可靠时**什么都不做**，而非"清理干净"
- 自动防护：`daemon-ctl.sh` 已内置拒绝误杀

## FM-5 · 凭据/敏感数据泄露（1 次，代价最高）

**表现**：为排查而打印配置文件，脱敏规则按字段名猜，漏掉 JSON 内嵌 token。

**实例**：Round 22 把 providers-hub 的多家 API token 打进对话记录。

**对策**：
- **先统计后展示**：只输出计数、类别、状态
- 处理凭据文件时假设脱敏一定会失败
- 优先用结构化数据源（`state.json` / `token-ledger.json`）而非凭据文件

---

## FM-6 · 凭印象陈述自己的历史（1 次，性质最危险）

**表现**：把没发生过的事说成"我之前做过"。

**实例**：Round 19 声称"i管家是我停用的应用之一"，实测从未停用。

**为什么危险**：它披着"如实交代"的外衣，最容易被信任。

**对策**：
- 关于自己历史的陈述**必须查记录**（`scripts/history-query.sh`）
- 记录里没有 = 很可能没发生过

---

## FM-7 · 告警淹没真实风险

**表现**：报一堆不会出事的告警，真风险被淹没。

**实例**：Round 25 报"6 个账户 6h 到期"，全是可自动续期的；
真正危险的不可续期账户反而没突出。

**对策**：
- 只报"会真出事"的（如 `refreshable=false` 且临近到期）
- 区分"正常周期"与"真失效"
- 去重：同告警不重复推送

---

## FM-8 · 用不可靠的小样本下判断

**表现**：请求 3 次、错 3 次 → 判为 100% 失败账户。

**对策**：设最小样本量（记分卡用 `<10 次不参与评分`）。

**实例**：Round 41 用"首末两点"从 1.3 小时数据算出 85 MB/小时，
并外推"20 小时后 OOM"。原始序列其实在 1162~1605MB 间**振荡**，
端点拟合无视了这一点。正确做法是分段中位对比 + 明确声明外推边界。
