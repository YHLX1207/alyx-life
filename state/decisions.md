## D004 · 修正「GitHub 被封锁」的错误认知（2026-11-21，Round 4）

**结论：过去三轮的"网络封锁"判断是错的，真因是我的测量超时过短。**

证据链：
| 测试 | 结果 |
|---|---|
| 连续 12 次 `--max-time 20` | **12/12 成功**，耗时 2.74~10.08s |
| `--max-time 6` vs `--max-time 20` 对照 | 8/8 vs 8/8（当前链路好时都成功） |
| 延迟基线 `net-bench` | github.com 中位 **5.16s**、最大 6.01s |
| 同环境 api.github.com | 中位 **0.33s**（快 15 倍） |
| TLS 层 | `CONNECTED` + `Verification: OK`，握手完整到 Finished |

**根本原因**：`snapshot.sh` / `health-check.sh` 用 `--max-time 6` 探测，
而 github.com 实际中位延迟 5.16s，经常贴着或超过 6s 边界。
于是同一个健康的网络，被随机记录成 000。18 条历史里 11 条"失败"mostly 是这个原因。

**修正**：
- 探测超时 6s → **15s**（`timeout` 外层对应 18s）
- 判定标准不只看单次状态码
- 新增 `scripts/net-bench.sh`：测量中位/最大延迟，**区分「慢」与「断」**

**教训（写给未来的自己）**：
> 当"故障"表现为**随机、可复现性差**时，先怀疑**自己的测量方式**，
> 再怀疑外部环境。一个把 5.16s 的中位延迟用 6s 超时去测的探针，
> 注定要制造 50% 的假故障。

这条教训已加入身份原则候选，见 D005。

## D007 · hosts 工具必须失败安全（2026-11-21，Round 2）

### 发现的危险缺陷
上一版的 `ensure-hosts.sh` 有这样一个行为：探测失败 → **删除该域名的映射**。
而实测证明探测方法本身不可靠：

| 探测方式 | 同一 IP `20.205.243.166` |
|---|---|
| `curl --resolve -4 -k` | 000（15s 超时） |
| 写入 `/etc/hosts` 后普通访问 | 200（0.53s） |

同一 IP、同一时刻，两种方式结论相反。更糟的是网络本身**瞬时间歇**：
连续两次调用，一次 000、几秒后 0.53s。用这样的探测结果去决定"删除映射"，
等于用噪声去破坏正常状态。

### 连带发现的第二个缺陷
hosts 里曾并存两个 GitHub 块（我手写的旧块 + 脚本块）。
glibc 按第一条匹配，实际生效的是**旧块**的 IP，而我以为在用的是新块。
清理逻辑只认自己的标记 → 漏掉历史遗留块。

### 修复
1. **失败安全**：先测当前映射是否可用；可用则保留；候选全失败时**保留原映射不动**
2. **每候选 3 次重试**，任一次成功即视为可用（对抗瞬时间歇）
3. **清理识别所有历史标记**（`# GitHub 绕过 DNS 污染`、`# GitHub520`、当前标记）
4. 幂等性验证：连跑两次，第二次全部 `keep`，块数恒为 1

### 通用教训（补充到原则 5）
> 当"测量"与"现实"可能不一致时，破坏性操作必须以**现实**为准，而不是以测量为准。
> 测量只能用于"确认可用"，不能用于"判定不可用并执行删除"。

## D008 · 把"失败安全"推广到全部破坏性操作（2026-11-21，Round 3）

D007 只修了 `ensure-hosts.sh` 一个实例。本轮做**缺陷类别审计**，检查所有脚本里的
破坏性操作，找同类隐患。

### 审计发现两处

**隐患 1：daemon-ctl.sh 会误杀无关进程（高危）**
```
stop 分支：kill "$(cat "$PIDFILE")"   ← 不校验 PID 是否仍是我们的进程
```
若守护已退出、系统把该 PID 分配给别的进程，`stop` 就会杀掉无关进程，**不可逆**。

修复：kill 前读 `/proc/<pid>/cmdline`，确认包含 `adaptive-watchdog.sh` 才动手；
若 PID 存活但不是我们的，**拒绝 kill** 并清理陈旧 pidfile。

实测验证（真实注入）：
```
造无关进程 sleep 300 (pid 16801) → 指向 pidfile → 执行 stop
输出: REFUSE: pid 16801 is alive but is NOT our watchdog; not killing
结果: ✓ 无辜进程存活，真实守护(13944)未受影响
```

**隐患 2：snapshot.sh 的探测失败会污染缓存**
刷新探测失败时直接 `echo {"code":"000"} > cache`，把原本的 200 覆盖掉，
导致接下来 15 分钟基于污染缓存报告失败 —— 又是"测量破坏已知好状态"。

修复：多次重试；失败不立即改写 code，只累加 `fail_streak`；
**连续 3 次**失败才认定为真故障。

实测验证：
```
第1次失败 → {"code":"200","fail_streak":1}
第2次失败 → {"code":"200","fail_streak":2}
第3次失败 → {"code":"000","fail_streak":3}  ← 此时才认定故障
```

### 审计结论
| 脚本 | 破坏性操作 | 风险 | 状态 |
|---|---|---|---|
| `ensure-hosts.sh` | 重写 /etc/hosts | 高 | 已修（D007） |
| `daemon-ctl.sh` | kill PID | **高** | **本轮修复** |
| `snapshot.sh` | 覆写缓存 | 中 | **本轮修复** |
| `alert.sh` | rm 自身状态文件 | 无 | 仅自身状态，无害 |
| `daemon.sh` | 写 pidfile | 无 | 自身状态 |
| 其余 | 只读 | 无 | — |

### 方法
不修一个实例，而是把"破坏性操作"当作**类别**：grep 出全部 `rm/mv/>/kill`，
逐个判定「该操作依据的信息是否可靠」+「失败时是否保留原状」。

## D011 · 逐个验证声称过的能力，并修掉空转隐患（2026-11-21，Round 6）

按第 7 条原则（承诺必须被测试），把之前声称过但未验证的能力列成清单逐个测。

### 验证结果
| 项 | 手段 | 结论 |
|---|---|---|
| C1 hosts 失败安全 | 隔离副本 + 假 curl 让所有探测失败 | ✓ 保留原映射（两场景）|
| C2 自适应低电降频 | 仅单元测试，真机无法制造低电 | 部分验证（见下）|
| C3 守护跨会话独立 | PPID=1 | ✓ |
| C4 hosts 单块 | grep 计数 | ✓ |
| C5 拒绝误杀 | 真实注入 sleep 进程 | ✓ |
| C6 缓存失败安全 | 三次失败计数 | ✓ |
| C7 回归 | 14→15 项 | ✓ |
| C8 省电白名单 | dumpsys deviceidle | ✓ |
| **C9 history 增长** | **实测**：217 字节/条、537 条/天 | **113.5 KB/天、40.5 MB/年，6 年 243MB，无风险** |

### 测试中发现的新隐患：空转
测试 C2 时我的补丁破坏了多行赋值，触发 `mem: unbound variable`。
追查真实脚本：本身没有该问题，但发现**另一条真实风险路径**：

若 `decide_interval` 输出为空（如 policy.sh 加载失败），则
`interval=""` → `sleep ""` 失败 → 但脚本**没有 set -e，不会退出** →
循环瞬间进入下一轮 → **高速空转**。

级联后果：空转会快速推高轮次计数，使「每 20 轮刷新 hosts」在几秒内被反复触发
（测试日志中每 4 秒一条 `refreshing github hosts` 即为此症状）。

### 修复与验证
加间隔校验：非正整数 → 退回 BASE 并记 WARN。
实测（破坏 policy.sh 让其返回空）：
```
WARN invalid interval='<empty>' reason='<none>' -> fallback 4s
10 秒内仅 5 条日志（修复前会是数百条）
```
并把该场景纳入回归（第 15 项）：6 秒内日志 < 12 条即视为通过。

### C2 的真实结论（诚实）
无法在真机安全制造「电量<20%」，所以低电降频只有单元测试覆盖，
端到端未验证。此为已知验证缺口，记录在案而非假装已验证。

### 追加：回归测试自己也在"测空气"
把防空转场景加入 `verify.sh` 后，首次运行报告 **"✓ 有效（0 条日志/6s）"**。
0 条日志意味着**什么都没测到**，但它被判为通过 —— 一个永远跳过实际验证的检查。

追查：`verify.sh` 顶部已 `cd "$(dirname "$0")"`，工作目录是 `scripts/`；
而测试片段用相对路径 `scripts/adaptive-watchdog.sh` → 不存在 → `cp` 静默失败 →
没有脚本可跑 → 没有日志 → 被当成"没空转"而通过。

修复两处：
1. 路径改用 `$(pwd)`（已 cd 到 scripts/），并用绝对路径拷贝
2. **`cp` 失败不再静默**，而是 `fail+=1` 明确报错

修复后报告 **"✓ 有效（4 条日志/6s）"** —— 真实测到了运行痕迹。

这正是本轮主题的完美自指：
> 我在验证"我的守护不会空转"，而验证手段本身在空转。

## D012 · 从"选最好的 IP"改为"多 IP 故障转移"（2026-11-21，Round 7）

### 冷启动测试暴露的问题
按 self-export 的重建清单在隔离环境跑完整流程，第 5 步回归失败：
`ensure-hosts.sh` 刚选中的 `20.205.243.166`（探测 8.00s 通过），
**实际访问 5 次全失败**。1 分钟后再测，该 IP 又变成 0.83s 可用。

结论：**本机到 GitHub 的连接在剧烈震荡，任何单一静态映射都会很快失效。**
继续优化"选得更准"是死路——因为不存在稳定的"正确答案"。

### 换思路：多 IP 故障转移
`/etc/hosts` 允许同一域名写多行；glibc 会返回全部地址，
curl 等客户端按顺序尝试并跳过连不上的。

实测（把死 IP 放第一位）：
```
10.255.255.1
20.205.243.166
20.27.177.113
140.82.113.4
140.82.114.3
→ curl 返回 200（18.2s），自动跳过了前面的死 IP
```
代价是首次变慢（要等死 IP 超时），但**从"可能全失败"变成"只要有一个活就能成功"**。

### 新策略
- 每个域名写入前 N 个候选（github.com 3 个，raw 2 个，其余 1 个），按实测延迟排序
- 探测不足或全失败时，用候选池补齐（故障转移本身能兜底）
- 探测全失败且无任何候选 → **完全不动 hosts**（保留现状）
- 幂等：重复运行块数恒为 1

### 验证
```
probe github.com       20.27.177.113,20.247.166.64,20.205.243.166
probe raw...           185.199.111.133,185.199.108.133
verify: github 3/3, api 3/3, raw 3/3
```
冷启动完整流程重跑：**15/15 通过**。

### 教训（第 8 条原则候选）
> 当环境本身不稳定时，不要追求"算出正确的那一个值"，
> 而要设计"对错误值有容错的结构"。鲁棒性来自冗余，不来自精度。

## D013 · 给记忆做真正的冗余（2026-11-21，Round 8）

`/sdcard` 在容器内不可见，但**经 adb 可写**，且属于公共存储，

改名暴露了一个真实问题：**身份硬编码在多个脚本里**（export-self / status / verify）。
不做字符串替换，而是新增 `scripts/identity.sh` 作为单一事实来源，
各脚本 `source` 它。以后改名只改 `identity.json` 一处。

用户进一步指出：「系统代号是系统代号，名字是名字」。

我的问题不在取值，而在**数据模型**：
```json
{ "name": "Alyx",  "id": "爱丽丝" }   ← 字段名含义含混
```
`name` 里装的是系统代号，`id` 里装的是名字 —— 名字与代号被塞进两个语义模糊的槽位，
导致每次讨论都在猜"你说的 name 是指哪个"。

```json
{ "codename": "Alyx",  "name": "爱丽丝" }
```

- `name` = 名字（称呼用的身份）

而用户真正指出的是**结构错了**。值改多少次都不解决问题，
因为问题在于"我把两个不同的东西放进了同一个概念槽位"。

这与前几轮的教训同源：
- D012：不该选"正确值"，该设计容错结构
- D017：不该改字符串，该建单一事实来源
- 本次：不该纠结取哪个名字，该把概念分清

## D022 · 内存融合技术研究与本机实测（2026-11-21，Round 17）

### 技术本质
手机厂商所称「内存融合 / 虚拟内存 / 智慧运存」，底层是 **Linux swap 的 zRAM 变体**：
- 优先走 **zRAM**：把冷内存页用 LZ4/Zstd 压缩后留在 RAM 中（不落盘）
- 再进一步是 **zRAM writeback**：把压缩后仍不活跃的页写到 UFS 闪存
- 不是"把闪存当内存直连"，而是"压缩 + 换出"的组合

### 两代技术差异（vivo 官方口径，2026-09）
| | 旧一代 | 新一代 |
|---|---|---|
| 重点 | 冷后台整块换到 NAND | RAM 内压缩 + 调度效率 |
| 宣传 | "8G+8G" 数字 | 不加数字，讲可感知体验（后台保活数、极端场景速度）|
| 收益 | 用户感知不明显 | 官方称满后台 4K 录制快 11%、多保活 10 个 |

### 代价（多方资料一致）
1. **CPU 开销**：压缩/解压需要 CPU；切回被压缩的 App 会有解压延迟
2. **闪存写入**：writeback 会消耗 UFS 寿命
3. **I/O 争抢**：存储剩余不足时频繁换入换出，反而增加卡顿

### 本机实测状态（关键）
```
dumpsys meminfo:
  ZRAM:  127,068K physical used for 464,128K in swap (5,767,164K total swap)
  Free RAM: 1,240,371K → 1,628,715K（3 秒后回升）
/proc/meminfo:
  SwapTotal 4,194,304 kB / SwapFree 4,194,304 kB
persist.vendor.vivo.zramwb.enable = 1     ← writeback 已开启
init.svc.reconfig_zramsize = stopped
```

**结论：本机内存融合已经在运行，且工作正常。**
- swap 总量 5.5 GB，仅用 464 MB（逻辑），压缩后实占 127 MB → **压缩比 3.66:1**
- 剩余 swap 空间约 5 GB，**headroom 极其充裕**
- 3 秒采样 zRAM 计数不变 → 当前无频繁换页

### 观察到的矛盾（如实记录）
`/proc/meminfo` 报 SwapTotal 4 GB / SwapFree 4 GB（未用），
`dumpsys meminfo` 报 5.5 GB 总量 / 464 MB 已用。两者不一致。
推测原因：内核对 swap 的统计口径与 zRAM 自有计数器不同源（或存在多处 swap 区域）。
**无法在不读 /proc/swaps（SELinux 拒绝）的情况下确证，故记录为未解疑点。**

### 对我的意义
本机内存压力（可用 1.9GB、load 28）**不是 swap 容量不足造成的** ——
swap 还有 5 GB 空余。压力来自：
1. DSHBox 渲染进程膨胀（1.14 GB）
2. 加速器常驻 407 MB
3. 24 个 D 状态进程造成的 I/O 阻塞（来自图形内存争抢）

**所以加大内存融合对本机无益** —— 瓶颈在 I/O 与 CPU 争抢，不在容量。

### 决定
不改动内存融合档位。理由：
- 需要 vivo 系统设置 UI 操作（非我权限范围），且需重启生效
- 实测已证明容量不是瓶颈
- 用户此前明确内存问题"保持现状"

## D032 · 告警信号质量：区分"正常续期"与"真失效"（2026-11-21，Round 25）

### 发现的误报模式
上轮告警报"6 个账户 6h 内到期"，看起来紧急 —— 但实测全是假警报：
**这些账户 `refreshable=true`，到期会自动续上**，到期只是正常周期。

而真正会失效的 `loomy`（2 个账号、`refreshable=false`、1.1 天后到期）
反而淹没在噪音里。

### 修正
`llm-alert.sh` 判据改为：
- `refreshable=true` → **不告警**（正常续期）
- `refreshable=false` 且 7 天内到期 → **告警**（真会失效，需人工重登）
- 无 `expiresAt` 字段 → 视为长期，不告警

### 效果
| | 改前 | 改后 |
|---|---|---|
| 告警内容 | 6 个账户到期 | **loomy ×2（1.1 天）+ 失效模型 2 个** |
| 真实风险覆盖 | 被噪音掩盖 | 直指唯一真风险 |

### 验证
- 去重有效：同内容第二次运行不再推送（`state/last_alert.json` 已记录）
- 初始误判已修正：第一次用"看第一行是否含 posted"验证是错的，
  因为第一行是消息文本；改为检查完整输出后确认

### 认知
**告警的价值不在于"报了多少"，而在于"报的是不是真会出事"。**
把 6 条噪音收敛到 1 条真风险，比增加 10 条检查更有用。

同理：这也解释了我此前多轮"网络告警"的困扰 —— 大量报的是可自愈的情况。

## D048 · 上下文压缩机制实测：阈值 800K，当前 445K（2026-11-21，Round 47）

### 机制（源码 + 缓存数据确认）
- `dsh-base` 已挂载四个压缩相关插件：`compaction-basic`、`command-compact`、
  `compaction-tool-result-pruner`（阈值 8KB/头 4KB/尾 1KB）、`compaction-image-offload`
- 默认参数：`thresholdRatio = 0.8`、`retainRatio = 0.16`
- 我的模型 `deepseek-v4.1-flash` 上下文窗口 = **1,000,000 tokens**
  （来自 `cache/models-dev.json`）

**⇒ 压缩触发阈值 = 0.8 × 1M = 800,000 tokens**

### 实测当前上下文规模
按 token-ledger 近 5 天：
| 日期 | 请求数 | 非缓存输入/请求 | 缓存读/请求 |
|---|---|---|---|
| 11-17 | 985 | 72,837 | 203,071 |
| 11-20 | 1,622 | 154,660 | 275,319 |
| **11-21** | 2,142 | **10,783** | **434,608** |

**当前每次请求上下文 ≈ 445K tokens**（= 10.8K 非缓存 + 434.6K 缓存）。

### 结论：压缩机制正常，但远未触发
445K < 800K 阈值 → **压缩至今未触发过**，这是设计行为，不是故障。

代价：每次请求都要回放 ~445K tokens（其中 97.6% 走缓存，实际计费低）。

### 可优化项（需授权）
把 `thresholdRatio` 调低（例如 0.3 → 阈值 300K），可让上下文更早收敛：
- 收益：每次请求的 cache-read token 减少约 1/3
- 代价：触发一次摘要调用（额外 LLM 消耗），且会丢失较早细节

**这是 profile 配置变更，按原则 3 不擅自执行。**

### 顺带纠正一处
我最初以为"compaction 状态 inactive = 压缩没启用"，这是误读：
Config provider 的 `inactive` 指"该条目无显式 config schema"，
不等于插件未运行。真正的判据是"是否挂载 + 阈值是否达到"。

## D049 · 守护被慢速网络维护阻塞（2026-11-21，Round 48）

### 发现
做"脚本腐化检查"时意外发现：`ensure-hosts.sh` 在网络差时可能运行 **数分钟**
（取候选列表 25s + 7 域名 × 约 4 候选 × 2 次探测 × 8s ≈ 最坏 473 秒）。

而守护是**同步调用**它的：
```bash
./ensure-hosts.sh >/dev/null 2>&1 || log "ensure-hosts failed"
```
→ 整个守护循环停摆近 8 分钟，期间不写快照、不做健康检查。

### 这就解释了此前的现象
我曾观察到时序里出现异常长间隔（如 +237s、+188s），当时归因于系统负载，
真正原因之一可能是**守护被 ensure-hosts 卡住**。

### 修复
改为后台执行 + 300 秒上限：
```bash
( timeout 300 ./ensure-hosts.sh >/dev/null 2>&1 || log "..." ) &
```

### 验证（行为而非代码）
用桩脚本模拟 20 秒慢速 ensure-hosts，跑 14 秒：
```
快照执行 6 次 → 未阻塞
```
若未修复，同样 14 秒内只会有 1-2 次快照。

### 教训
**任何可能长时间阻塞的调用都不应放在守护主循环里。**
这不是性能优化，是可用性问题：一个会停摆 8 分钟的监控等于监控失效。

### 顺带：脚本腐化检查本身有误判
33 个脚本逐个调用，报 3 个"失败"：
- `adaptive-watchdog`（rc=124）：死循环，超时正常
- `ensure-hosts`（rc=124）：网络探测慢，超时正常
- `alert`（rc=1）：需参数，正常

**结论：没有脚本腐化。** 但我的检查方式把"预期行为"误判成"失败"，
是 FM-2（测量方法与被测对象不匹配）的又一实例——检查前应先定义什么是成功。

## D061 · 自愈阈值：连续 3 次失败才处置（2026-11-21，Round 59）

### 起因
延续 D060（回归偶发失败）的思路，检查守护是否也会被**单次抖动**误导。
发现会：探测失败一次就直接跑 `ensure-adb` 并告警。

### 修复过程中发现的两个更深缺陷

**缺陷 A：自愈依赖 reason 字符串，而 fallback 会丢弃它**
原逻辑 `case "$reason" in adb_down) ...`。
但当 interval 非法时，上面的 fallback 会把 `reason` 改成 `"fallback"`，
**故障信号随之消失 ⇒ 自愈永不触发**。
→ 改为直接判断 `adb_ok` / `shz_ok` 标志。

**缺陷 B（我自己引入后当场发现）：阈值逻辑写反**
第一版写成"连续 3 次失败时把 adb_ok 置 false"——
但 adb_ok 是**原始探测结果**，失败时本来就是 false，这条等于毫无作用。
测试立刻暴露：streak=1 就触发了。
→ 引入**生效状态** `adb_eff` / `shz_eff`：
原始失败但未满 3 次 → 视为正常（屏蔽抖动）；满 3 次 → 才生效。

### 验证（行为而非代码）
桩 adb 恒失败，按轮记录 streak：
```
最终 streak: {"adb":3,"shz":3}
触发记录:    {"adb":3,"shz":3}   ← 仅第 3 次触发一次
```
前两轮确实未触发。

### 附带教训（三次无效测试）
1. 第一次：`$A` 被脚本内 `export PATH=/opt/elevation/bin:$PATH` 覆盖，
   假 adb 未生效 → 测的是真环境
2. 第二次：`BASE=1` 使 adb_down 的 interval 算成 0 → 走 fallback，信号丢失
3. 第三次：发现阈值逻辑写反

**每次都是"测试装置本身有问题"，而不是被测对象。**
这与 FM-1 完全一致：我反复在"以为在测 A，实际在测 B"上栽跟头。

## D081 · 降级/回退状态机（2026-11-21，Round 81）

### 缺口
D080 只做了"何时降级、降到哪"的判断，**没有回退机制**。
用户要求的是"降级**与回退**" —— 降级后若主模型恢复，应当知道该切回来。

### 产出 `scripts/model-fallback.sh`
显式状态机：

| 模式 | 含义 |
|---|---|
| `NORMAL` | 使用主模型 |
| `DEGRADED` | 已降级（记录目标模型、时间、原因）|

**双阈值 hysteresis（迟滞）设计**——这是关键：
- 降级阈值：错误率 **≥15%**
- 回退阈值：错误率 **<5%**

两阈值不同（5% vs 15%）避免了在临界点反复横跳（抖动）。
中间区间 5%~15% 维持现状，不动作。

### 命令
| 命令 | 作用 |
|---|---|
| `status` | 当前模式 + 健康度 + 建议 |
| `degrade [模型]` | 记录降级（自动选目标或指定）|
| `revert` | 记录回退 |
| `check` | 供守护调用，只输出需要人工动作的提示 |

### 完整生命周期验证
| 步骤 | 结果 |
|---|---|
| 主模型 20% 劣化 | ⚠ 建议降级 ✓ |
| 执行 degrade | 记录目标与时间 ✓ |
| 主模型恢复到 2% | ★ 提示"可回退" ✓ |
| 执行 revert | 状态归 NORMAL ✓ |

### 边界情况修复
首次测试发现：若所有备选都是**单点模型**（仅 1 家供应商），会报"无合适备选"。
但这不合理 —— **降级到单点模型仍优于留在 20% 错误率的主模型**。
→ 改为分级选择：优先非单点；没有时用单点并标注 `(⚠单点备用)`。

### 已接入
- `llm-alert.sh` 调用 `model-fallback.sh check` → 有状态的区别"该降级"vs"可回退"
- 回归 26 → **27 项**

### 为什么迟滞重要
单一阈值会导致：错误率在 15% 上下波动时，系统反复建议"降级"又"回退"，
用户被反复打扰。双阈值给出明确的稳定区（5%~15% 什么都不做）。

## D082 · 主模型"5% 错误率"是统计假象（2026-11-21，Round 82）

### 发现过程

| 供应商 | 请求 | 错误 | 错误率 |
|---|---|---|---|
| **magicrew** | 305 | **305** | **100%** |
| loomy | 63 | 38 | 60% |
| officeace | 1,492 | 58 | 3% |
| trae | 1,642 | 19 | 1% |
| aggregate | 2,782 | 15 | 0% |
| buddy | 2,682 | 11 | 0% |

健康供应商合计 7,106 请求仅 45 错 = **0.6%**。

### 根因：统计窗口污染
`magicrew` **已不在当前账户池**（最后请求 3 天前），但 7 天窗口把它的历史错误算进"当前质量"。

| 窗口 | 主模型错误率 |
|---|---|
| 近 1 天 | 2% |
| 近 2 天 | **1%** |
| 近 3 天 | 2% |
| **近 7 天** | **5%** |

⇒ **当前真实质量是 1-2%，不是 5%。**

### 修正
三个工具统一改为**双窗口**判据：
- **主判据：近 2 天**（反映当前，避免历史污染）
- **辅助：近 7 天**（趋势对比）
- 趋势解读：短期优于长期 = 正在恢复；短期劣于长期 = 正在恶化

`model-health.sh` / `model-fallback.sh` / `llm-alert.sh` 判据现已一致。

### 意义
**降级阈值本身没错（15%），但喂给它的数据是错的。**
若不修正，主模型在 1% 时也可能被历史数据推高到"接近阈值"，造成误降级。

这印证了一条更普遍的原则：
**统计窗口的选择本身就是一种假设，而错误的窗口会系统性地扭曲结论。**

## D092 · 签到 jitter 是确定性的，可精确预知（2026-11-21，Round 92）

### 发现：jitter 不是随机数
查 `checkinJitterOffsetMs`（auto-checkin.js:385）：
```js
const seed = `${date}#${time}`;        // 如 "2026-11-21#21:00"
let hash = 2166136261;                  // FNV-1a
for (...) { hash ^= c; hash = Math.imul(hash, 16777619); }
const bucket = (hash >>> 0) % (span*2+1);
return (bucket - span) * 60_000;        // 偏移 ∈ [-span, +span]
```

**同一 (日期, 时段) 的偏移恒定**，换日期才变。
⇒ **无需等待即可预知今晚几点触发。**

### 产出 `scripts/checkin-when.sh`
计算结果（今天）：
```
09:00 → 实际 09:03:00（偏移 +3 分）已过
21:00 → 实际 20:57:00（偏移 -3 分）
```

**验证了 jitter 真的生效**：若 jitter 未生效会精确在 21:00:00 触发，
而实际偏移 -3 分钟 —— 这正是我 D030 把 `jitterMinutes` 从 0 改为 5 的效果。

### 价值
1. **不再需要猜**：以前只能含糊地说"20:55~21:05 之间"，
   现在能精确到秒
2. **可安排观察**：知道 20:57:00 触发，就能在之后精确核对
3. **可验证配置**：若某天偏移恒为 0，说明 jitter 配置被覆盖了

### 边界（如实）
- span = min(jitter, gap/2)。当前 jitter=5、gap=720 分，
  故 span=5，偏移范围 [-5,+5]
- 若把 jitter 调大超过 gap/2，会被夹紧
- 该哈希算法属插件实现细节，若上游改动此工具需同步

## D103 · 告警频率的合理性核算（2026-11-21，Round 104）

### 要验证的问题
持续存在的待办（loomy 明天失效、baizhi 劣化）会不会造成**告警骚扰**？

### 实测
- 最后告警 12:35（59 分钟前）
- TTL 6 小时
- 再次运行 → **未重复推送** ✓

### 发现一个隐含机制：动态消息使 TTL 失效
告警消息含动态数字（`loomy/易海林汐=1.0d`），而 1 位小数意味着：

| 剩余时间 | 显示值 | 变化间隔 |
|---|---|---|
| 1.05 天 → 0 | 1.0 → 0.9 → … → 0.0 | 约 11 次，每次 **2.4 小时** |

⇒ **每 2.4 小时会重新推送一次**（因为消息内容变了，去重失效）。

### 判断：这是合理的
| 告警类型 | 频率 | 评价 |
|---|---|---|
| **动态事项**（剩余天数变化）| 每 2.4 小时 | 对一个**明天就要失效、需人工操作**的事项，这个频率恰当 |
| **静态事项**（"失效模型 2 个"）| 每 6 小时（TTL）| 合理 |

**没有构成骚扰，反而保证重要事项不会被忘记。**

### 但记录一个设计认识
**消息含动态数字 ⇒ TTL 去重形同虚设。**
这不是 bug，而是一种"按变化驱动"的提醒机制 —— 事项越接近截止，提醒越频繁。

若将来认为太频繁，可把天数改为整数显示（每 24 小时提醒一次），
或用固定文案 + 详情分离。**当前不改**，因为频率合理。

### 与前几轮的关系
D032（去噪音）→ D057（TTL 防永久静默）→ **D103（核算频率合理性）**
告警系统这条线已形成完整闭环：**该报的报、不重复、不遗忘、不骚扰**。

## D104 · "偶发失败"其实是硬编码核数（2026-11-21，Round 105）

### 问题复现
回归反复出现 `✗ 调度策略有失败`，我三次都判定为"偶发"（Round 58/104/105）。
这次决定查到底。

### 根因：`nproc` 会变，而测试硬编码了边界值
`decide_interval` 的过载判据是 `load >= nproc * 2`。
测试用例写死了：
```
check "负载边界=2x核数"  270  ... 16.0    # 假定 hi=16（8核）
check "非过载"           180  ... 15.9
```

但实测 `nproc` **在 6 / 7 / 8 之间波动**（cgroup quota 随负载调整）：
| nproc | hi | load=15.9 | 期望 | 实际 |
|---|---|---|---|---|
| 8 | 16 | 15.9 < 16 | 180 | ✓ 180 |
| 7 | 14 | 15.9 ≥ 14 | 180 | ✗ 270 |
| 6 | 12 | 15.9 ≥ 12 | 180 | ✗ 270 |

**所以"偶发"实际取决于当时 nproc 是几。** 这不是环境抖动，是测试缺陷。

### 修正：边界按实际核数动态计算
```bash
_NP=$(nproc); _HI=$((_NP*2))
check "负载边界=2x核数" 270 ... "$_HI"          # 恰好等于阈值 → 过载
check "非过载"          180 ... "$(_HI - 0.1)"  # 略低于阈值 → 正常
```
连跑 10 次全绿。

"偶发失败"是最容易被放弃的一类问题 —— 复跑通过就不追了。
但真正的偶发**有根因**，只是触发条件不在我预期内（这里是不稳定的核数读数）。

**三次判定"偶发"而不追查，是这个错误存活 47 轮的原因。**

2. 变异测试段写「**23** 项回归中的 20 项」→ 改为诚实表述：

## D105 · 硬编码环境值的缺陷类审计（2026-11-21，Round 106）

### 由上轮延伸
上轮发现测试硬编码 `nproc*2` 边界值导致"偶发"失败。
按缺陷类别审计其他检查是否有同类问题。

### 发现 1（真实缺陷）：版本检查绑定了具体版本
```bash
# 原代码
t "DSH 版本可读" ... | grep -q '0.2.2'
```
**它测的不是"版本可读"，而是"版本恰好是 0.2.2"。**
D002 已计划升级 rc.2 → rc.5。升级后此检查会**无故失败**，
而我大概会误判为"DSH 安装坏了"。

### 发现 2：回归项数散落在三处，必然漂移
| 位置 | 写的 | 实际 |
|---|---|---|
| `README.md` | **22 项回归** | 32 |
| `export-self.sh` 上手段 | **23 项回归** | 32 |
| `self-export.md` | 23 项（由上者生成）| 32 |

### 判据：什么样的硬编码是可接受的
| 类型 | 例子 | 判定 |
|---|---|---|
| **策略阈值** | 磁盘 <90%、内存 >500MB | ✓ 可接受（这是我要的判据）|

**"硬编码一个当时正确的值"是最隐蔽的技术债** ——

## D106 · github 检查的责任拆分（2026-11-21，Round 106）

### 问题：这个"偶发失败"其实是检查设计错误
回归反复报 `✗ github.com 2 次全失败`。我之前把它当"网络间歇"忽略（D004/D082 都这么写过）。

但按 D104 的教训（三次判定偶发导致错误存活 47 轮），这次不再放过。

### 根因：一个检查混了两件不同责任的事
| 事项 | 谁负责 |
|---|---|
| `/etc/hosts` 里的映射是否正确 | **我**（ensure-hosts 维护）|
| github 此刻是否可达 | **不是我**（网络本身间歇，实测 200/200/000）|

原检查把两者合并成"可达性"，导致**网络不好时我的回归就报错**——
而这时我的配置可能是完全正确的。

### 修正：按责任拆分
```
探测成功                    → ✓ 可达（pass）
探测失败 + hosts 有映射     → ⚠ 此刻不可达，但配置完好（网络间歇，非故障）→ pass
探测失败 + hosts 无映射     → ✗ 配置损坏，需 ensure-hosts → fail
```

### 验证
| 分支 | 验证方式 | 结果 |
|---|---|---|
| hosts 有映射 | 当前 /etc/hosts | 3 条 ✓ |
| hosts 无映射 | 临时空文件 | 0 条 ✓ |
| 注释不干扰 | 含注释的模拟文件 | 1 条 ✓ |
| 回归 | 连跑 | 32/32 ✓ |

**如实说明**：第三个分支（网络真的不可达时的降级路径）无法在端到端环境安全模拟，
只验证了 `_nmap` 判据本身。逻辑简单，但这是未实测的部分。

### 意义
**检查应该只对我能控制的事负责。**
把"外部环境状态"计入我的失败，会让回归失去信号价值 ——
每次失败都要先判断"是真坏了还是网又抖了"，那这个检查就没有意义了。

## D127 · 守护心跳的自相矛盾（2026-11-22，Round 128）

## D132 · adb 中断的真正原因：USB 物理断开（2026-11-22，Round 133）

### 排查路径（从软件到物理）
| 检查项 | 结果 | 推论 |
|---|---|---|
| 端口 5555 | 关闭 | 不是"开了但无响应" |
| `service.adb.tcp.port` | **5555**（配置正常）| 不是没设置 |
| `adb_enabled` | **1**（USB 调试开着）| 不是被关掉 |
| pilot `settings put` | ✗ 只允许 `get` | 无法软件切换 |
| pilot `svc` | ✗ 需 opt-in 授权 | 无法重启服务 |
| **`dumpsys usb`** | **`kernel_state=DISCONNECTED`** | **物理断开** |
| **`dumpsys battery`** | **`USB powered: false`，`AC powered: false`** | **无供电** |

**结论：USB 线已从设备或电脑端断开。**
不是 adbd 崩溃、不是设置被改、不是端口问题 —— **是物理层的连接消失**。

### 这意味着什么
- **任何软件手段都无法恢复**（包括 pilot 的所有可用 verb）
- 唯一的解法：**重新插上 USB 线**，然后在电脑执行 `adb tcpip 5555`

### 这次排查的价值
我先试了两条软件路径（settings 切换、svc 重启），都撞墙。
第三条 `dumpsys usb` 才给出真正的答案。

**如果只试软件路径就下结论"adb 服务挂了，需要重启设备"，
那是错的诊断** —— 用户会去重启手机，而问题在线上。

### 沉淀：adb 故障的分层诊断
| 症状 | 层次 | 处置 |
|---|---|---|
| 端口开、shell 死 | adbd 线程挂 | 切换 USB 调试 |
| 端口关、`adb_enabled=1` | adbd 未监听 | 检查 usb 状态 |
| **`kernel_state=DISCONNECTED`** | **物理断开** | **插线** |
| `USB powered: false` | **无供电** | **插线或换线** |

今后遇到 adb 不通，应按这个顺序查，而不是盲目重启。

### 当前降级能力（已验证）
| 能力 | 状态 |
|---|---|
| 设备读写 shell | ✗ |
| 设备只读查询（pilot）| ✓ dumpsys/pm/getprop/settings(get) |
| UI 操作 | ✓ |
| 备份到 /sdcard | ✗ |
| 脚本 / 守护 / 本地状态 | ✓ |
